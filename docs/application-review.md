# Application Review

## Multiple Teams, Positions, And Hiring Rounds

Use the **Hiring Review** selector at the top of every page to switch applicant pools. **Hiring Reviews** in the sidebar lists all reviews, their team/position, assigned reviewers, applicant totals, and completion counts. **New Hiring Review** and **Review Setup** use the same four-team dropdown: Water Treatment, Wastewater Treatment, Maintenance, and Laboratory Services. Choose a position, month, and year to generate the title, for example **Maintenance Tech - Maintenance - October 2026**. The title is read-only and generated on the server as well as in the browser. Month/year default to the current period in America/Denver. Years 2000–2100 are supported.

Each review has its own one to four reviewer assignments, scoring, applicants, notes, votes, IDs, progress, and rankings. The same person can be assigned to multiple reviews. The optional **Use The Current Review's Reviewer Assignments And Scoring** checkbox copies only those settings. It never copies applicants, notes, or votes. Subsequent changes to one review do not alter another. Where names match, switching positions keeps the same person selected; a saved vote in one position never reveals votes in another.

In **Hiring Reviews**, use **Archive Review** to preserve an entire hiring round while removing it from the active selector. Archived reviews are read-only, including through older API clients. Use **Show Archived Reviews** to open or **Restore Review** to resume editing. Applicants, assignments, scoring, notes, and votes remain intact. All reviews may be archived; a new review can still be created. Archive and restore use revision checks, update the directory, and retain the normal recovery backups.

Team, position, month, and year can be edited in **Review Setup**. Existing reviews without a saved month/year retain their current title until setup is saved with those fields. Older Water and Wastewater team labels map to Water Treatment and Wastewater Treatment; unknown legacy labels remain readable and can be corrected in setup. Existing records migrate into one original review with their original title and IDs, without guessing which team they belong to. Assign its team/position in Review Setup. The original single-review API continues to address that original set only, protecting older browser pages from accidentally editing a different position.

Imports, sample resets, applicant deletion/archiving, backups, and reports are scoped to the selected review. The selected team's position is included in printouts, and individual JSON backups include hiring-review metadata. Importing a backup into another review imports the applicant/settings snapshot into that selected destination; it does not restore every position. There is no cross-position ranking or automatic deduplication of people with matching names.

The selected review is recorded in the URL (`?hiringReview=review-…`) so links reopen the intended position. Switching reviews protects unsaved forms with a discard confirmation. Position-level revision checks permit users to save different positions independently, while stale writes to the same position are rejected.

Server storage now uses a version-2 collection in the existing `review.json`. Old version-1 records are read as the original review; the first write stores the collection only after preserving the exact original file in the revision backup. Browser preview uses `northglenn-application-review-sets-v2`, migrating the old browser state when needed and retaining the original `northglenn-application-review-v1` for recovery. The previous whole collection is saved in `northglenn-application-review-sets-v2-previous` before local writes. Existing deployment backups cover the complete collection.

Endpoints: `GET /api/application-review/sets` lists reviews; `POST /api/application-review/sets` creates one; `GET/POST /api/application-review/sets/:id` reads or updates a particular review. The new `hiring-reviews.js` model is shared by the browser and server.

Workbook: `Application Review Template FINAL.xlsm`, including its Instructions sheet. The application implements the workflow using the shared Operations header, Inter font, fixed desktop sidebar, and mobile scrolling navigation.

Open `apps/application-review/index.html` with Live Server for a browser-only preview. When the API returns 404 on localhost, the page explicitly identifies **Browser Preview** and stores edits in that browser's local storage. It never switches an existing shared session to browser storage after an API failure. File URLs are not supported; use an HTTP server.

Only **Browser Preview** displays a storage notice, because its records are not shared. The normal shared-server view has no storage banner. Browser storage is separate for each browser profile and site address/port; changing from localhost to 127.0.0.1, for example, opens different browser data. Shared storage is the server's persisted review file, used by all clients of that server.

In **Review Setup → Import And Backup → Load Test Applicants**, confirmation replaces all active and archived applicants and their reviews with Flo Meter, Phil Ter, Clara Fication, Cole Agulation, and Beck Wash. Saved reviewer/scoring settings remain unchanged. A backup downloads first when records exist. The action saves to the page's active storage mode and survives refresh. There is no automatic sample reset on page load.

For shared records, start `npm start` for the API and `node dev-server.js` for the site, then visit `/application-review/`. The Docker suite includes the same static route and `/api/application-review` endpoint. The Apps menu links to the page. This implementation does not add an Operations Home card or deploy itself.

## Workflow

The review pages use tighter spacing above the applicant list. Application Details groups location, requested wage, and certifications before Your Review. The selected recommendation has both a strong outline and a checkmark. Results label unavailable scores **Awaiting Your Review** and mark incomplete totals **Partial Points**. Detailed comments keep each reviewer's name, recommendation, and full text together, with a quieter **No Comment** placeholder. Applicant rows use stronger separators and hover/focus highlighting.

Page introductions use the review title and relevant task guidance without a repeated Northglenn Operations overline or a second team/position subtitle. The position selector shows the review title directly, without prepending the team again. The same redundant introduction branding has been removed from the other themed Operations apps and the shared application menu.

**Results** is a reviewer-facing, read-only candidate table with search, sorting, scores, ranks, and printable results. Applicant details opened here expose no voting form, editing, deletion, archive, selection, transfer, creation, or settings actions. Existing result-hiding rules still apply: results require the selected reviewer's own saved vote, and ranks require all their active applicants to be reviewed. The completion shortcut opens this overview.

Each Results applicant has a summary row followed by a full-width notes area. After the selected reviewer saves their own vote for that applicant, the notes area displays all assigned reviewers' names, recommendations, and complete notes in a two-column layout (one reviewer fills the width). Saved notes without a vote also appear after this gate. Empty notes are labeled, and text wraps with preserved line breaks and no truncation. Before the selected reviewer's vote, peer notes are omitted from the rendered table and replaced by a vote-to-view message. Changing reviewer or clearing a vote reapplies the rule. The management Applicants table keeps its compact layout, and the existing printable report is unchanged.

The **Show Reviewer Comments** checkbox in Results controls the notes area. It is off by default, emphasizing interview recommendations and Total Points. Turning it on shows full reviewer comments beneath each applicant. The chosen mode is remembered on that browser/device across reviews and page reloads; it does not change records, printouts, or vote-visibility rules. The toggle appears only on Results.

**My Reviews > Applicants** is an always-visible list. Each applicant displays the selected reviewer's saved recommendation and, when present, their own complete comments with preserved line breaks. Notes saved before a vote also appear here. Selecting a different reviewer changes the comments shown; this list never includes other reviewers' comments.

**Manage Reviews** requires PIN **2350** before opening Applicants, Review Setup, or Hiring Reviews. Unlocking lasts for the current page; **Lock Management** or reloading the page locks it again. Management entry points and mutations in the UI share the gate. This is a plain-text browser convenience to prevent accidental management changes, not server-side authentication; the existing API is unchanged. My Reviews and read-only Results do not require the management PIN.

To correct applicants entered under the wrong position, open **Manage Reviews > Applicants** in the source review. Check individual applicants or the Applicant heading checkbox to select all rows currently shown (search/status filters apply). Choose **Move Selected Applicants**, select a different active review, then **Move Applicants**. Filtering or changing reviews clears the selection. The transfer removes the selected records from the source and adds them to the destination in one atomic storage write, with revision checks for both reviews. The destination receives new IDs without overwriting existing applicants; the source ID counter is not reset. Details, archive status, notes, votes, and timestamps are preserved. Saved reviews map to destination slots by reviewer name rather than slot number; missing reviewer assignments block the entire transfer. Scores use the destination review's point settings. Archived reviews cannot send or receive moves. Deployment does not move any applicants automatically.

Applicant forms and bulk-entry tables use separate required **First Name** and **Last Name** fields. **Last Name, Then First Name** is the default overview sort; full-name, rank, progress, and ID sorts remain available. Reviewer lists and guided queues use surname order. Existing full names and workbook imports are preserved, with first/last fields inferred from the last word, or from `Last, First` when a comma is present. Check inferred fields for compound surnames or suffixes in Edit Applicant. Single-word legacy names remain readable; editing requires both fields. Name edits preserve applicant IDs, notes, and votes. Backups include both name fields and the full display name.

The default landing page is **My Reviews**. Choose **Position To Review** and **Choose Your Name**. The selected name is displayed as **Reviewing As**, with **Change** to select another person. The device remembers the name. One progress bar shows how many applicants you have reviewed, and **Continue Reviewing (N Remaining)** starts or resumes the next unfinished applicant. After completion, the same action area shows **View Results**. Only assigned reviewer names are selectable. This remains attribution without logins.

The guided form shows one applicant, their qualifications, large Yes / Maybe / No choices, and optional comments in that order with plain-language explanations. **Save & Next Applicant** persists the vote before advancing. A blank vote cannot advance; **Skip For Now** leaves the applicant unfinished and confirms before discarding unsaved text. Continue returns to unfinished applicants, including skipped ones. A completion message appears only after every active applicant has a saved vote for that reviewer. **Applicants** lists every applicant with your recommendation and saved comments. Actions read **Review** or **Edit My Review**. **View Other Reviews** is an optional expansion after saving one's own vote; guided entry does not expose results automatically. Existing vote and rank visibility rules still apply.

The sidebar groups **Applicants**, **Review Setup**, and **Hiring Reviews** under **Manage Reviews**. The normal reviewer landing page omits dashboard statistics and applicant-management actions; the management table and print/backup tools remain available within that group. Archived hiring reviews remain read-only and cannot start guided entry.

1. In **Review Setup**, assign one to four reviewer slots, leaving unused slots blank, and set Yes/Maybe/No points (defaults 4/1/0). Reviewer selection is an attribution choice, not authentication or private review access. All saved perspectives are shared.
2. Add applicants with name, country, optional US state, requested wage, and certifications. Country defaults to USA. The country selector includes 249 country/territory codes; the US state selector includes all 50 states, DC, and five populated US territories. Selecting another country clears/hides the state input; the server also stores no state for an international applicant. Lists, searches, detail panels, backups, and printouts include the country. Older records without a country default to US, and unknown legacy state text is preserved as an existing choice until corrected rather than silently dropped. Requested wage is kept as the workbook's numeric amount; no hourly/annual basis is inferred. IDs are permanent, sequential, and never reused by archiving.
3. In **My Reviews**, select the reviewer, choose an applicant, enter notes and a vote, and explicitly save. Blank votes remain incomplete, including when notes exist. Reviews can be edited or returned to Not Reviewed.
   Applicant creation, editing, archiving, and individual printing are available from **Applicants**, not My Reviews. The global **Reviewer** selector controls visibility on every page and in printouts. Other reviewers' votes, notes, status colors, and aggregate scores are withheld until the selected reviewer has saved their own vote for that applicant. No reviewer selected means results remain hidden. Unsaved votes and notes-only saves do not reveal results; changing to an unvoted reviewer or saving a blank vote hides them again. Ranks and rank sorting are withheld until the selected reviewer has voted for every active applicant, preventing comparison order from disclosing other results. This is a presentation rule within the existing shared, selection-based workflow, not an authorization boundary. Full backups and the shared API retain raw records for administration and recovery.
4. Dashboard scores sum recorded votes. A No-only review has score zero, while no votes means no score or rank. Ties use competition ranks (1, 1, 3). Final completion requires a saved vote from every assigned reviewer. Unused slots do not contribute to pending counts or appear in selectors, shared perspectives, or printouts. A two-person review completes at two of two votes. A saved setup requires at least one reviewer; slots with existing notes or votes cannot be cleared or reassigned. Pending totals are labeled partial. Shared notes retain separate reviewer attribution instead of a concatenated cell.
5. Archive applicants to remove them from active ranking while preserving records; restore in Review Setup. A reviewer slot with saved notes/votes cannot be reassigned, preventing old reviews from being attributed to someone else.
6. **Delete** is available on Applicants rows (including the Archived filter) and in the applicant panel opened from Applicants. It requires confirmation and removes that applicant and their notes/votes from the current review. Other applicants remain unchanged, and deleted IDs are not reused. Existing backup files may still contain the deleted record; deletion is not a purge of backups. Archive remains the option for preserving records in the app. Neither action appears in My Reviews.

## Workbook Import And Export

**Bulk Edit Applicants** on the management Applicants page opens the same grid, prefilled with existing records. Select checkboxes to edit a particular batch; with no selection, it loads everyone currently shown by the search/status filters. Edit up to 100 applicants at a time. IDs are displayed, and adding/removing rows is disabled in this mode. Only changed rows are submitted. Saving validates the entire batch and updates existing records in one revision, preserving IDs, reviewer votes/notes, archive status, and the next-ID counter. Invalid or stale batches save nothing and leave the entered grid open for correction. The management PIN and archived-review restrictions apply.

**Manage Reviews > Applicants > Bulk Add Applicants** opens an editable table for adding up to 100 applicants to the selected hiring review. It starts with five rows. Use Number Of Rows and Set Row Count to create up to 100 rows at once, or add/remove rows individually. Reducing the count removes blank rows only and refuses to discard entered applicant information. Enter name, optional requested wage, country, optional US state, and licenses/certifications. Country defaults to USA. International rows clear and disable the state selector. Empty rows are ignored, while partially filled rows require a name. Validation errors retain the entered table for correction. Existing applicants and votes are preserved. The server validates the complete batch and appends it in one revision and one storage write; an invalid batch or stale revision adds nothing. Archived reviews cannot accept bulk additions. Canceling a changed table asks before discarding entries. The single-applicant form remains available.

**Import Workbook Or Backup** accepts this template as XLSM/XLSX, or the app's JSON backup. It reads Dashboard rows 9–108 and Reviewer 1–4 rows 7–106. Reviews are matched by Application ID, independent of dashboard sort order. Cached applicant values are read; formulas and VBA are never executed. Workbook data is parsed in the browser, and normalized review data is sent to the configured storage only after import confirmation. The original workbook is not copied into the repository or a public static asset.

Import replaces the selected review after confirmation; when current applicants exist, a full backup of that review is downloaded first. Browser preview also keeps its previous collection state. Server mutations keep prior valid versions in the data directory. The importer requires browser support for `DecompressionStream('deflate-raw')` and limits workbook size to 10 MB / 64 MB expanded. The server accepts normalized JSON up to 5 MB.

**Download Full Backup** preserves settings, all applicants (including archived), notes, votes, and IDs. **Print Summary** includes the active pool and applies the selected reviewer's visibility rules to scores, ranks, votes, and notes; an individual applicant can be printed from their panel with the same rules. Use the browser's Save As PDF for a reviewable PDF.

The printed summary keeps the applicant comparison table. Reviewer details start on a separate page for each applicant, with a clear name/ID header, score/progress, qualifications, and aligned Reviewer / Interview Vote / Notes columns. Vote labels retain color and text, blank votes read Not Reviewed, notes preserve line breaks and wrap, and long notes continue across pages. Printing one applicant omits the overall summary table. The Import And Backup section uses separate, spaced action panels; Archived Applicants has its own card.

## Interview Planning

Open **Manage Reviews > Interviews** using the existing management PIN. Check applicants to select them for interviews after every assigned reviewer has voted for every active applicant in that hiring review. This condition is checked on the server too. Contact information can be entered earlier, and existing interviews remain editable if review work is reopened. Archived hiring reviews are read-only.

Email and phone are optional fields in both the applicant editor and Interview Details. Each selected applicant has a call status (Not Called Yet, Called, Voicemail Left, or Reached Applicant), a response (Awaiting Response, Accepted Interview, or Declined Interview), and contact notes. Saving status or scheduling changes adds dated contact/scheduling history. Selecting or removing an applicant also creates a history entry. History is preserved when an applicant is removed from the interview list; any scheduled time is cleared with confirmation. Declining an interview clears its current appointment while preserving prior scheduling history.

After acceptance, use the date/time pickers, duration (default 60 minutes), and optional location or meeting details. Dates and times are explicitly **Mountain Time / America/Denver**, regardless of the coordinator's device timezone. A date and time must be entered together. Overlap warnings compare the selected hiring review's appointments and allow saves for separate interview panels. Filters show selected applicants, those needing contact, pending responses, accepted applicants needing a time, scheduled interviews, or declined applicants. Scheduled results sort by date and time.

Contact details and interview history persist in each applicant's shared record and are included in JSON backups/imports. Editing application details with older clients or through bulk edit preserves these fields. New fields default to blank when reading existing records. Existing revision checks and backup writes apply to all interview actions. This stage records communication and schedules; it does not send emails or calendar invitations.

Verify the interview workflow with `node --test scripts/application-interviews.test.cjs` and `node scripts/check-application-interviews.cjs`. Both use temporary synthetic records. Deployment runs the interview model/API tests along with the existing review tests.

## Storage And Deployment

- Data: `data/application-review/review.json`, under the existing suite's persistent `/app/data` mount. Override with `APPLICATION_REVIEW_DATA_DIR` when needed.
- Backups: `before-<revision>.json`, retained before each mutation. Include this directory in retention and recovery planning; no automatic history deletion is implemented.
- All changes require the current revision; concurrent stale saves are rejected while the form remains intact. Refresh after closing or copying your unsaved entries, then reapply. The page refreshes idle shared views every minute, never an open dialog or unsaved setup.
- Same-origin writes and server-side validation protect against malformed requests. Saved data corruption returns an error instead of replacing records with a blank state.
- Existing suite deployment scripts package the API module, copy its model into the Node image, and back up its data before deployment. This page has not been deployed by creating it.
